# ExynosTools-LSFG

ExynosTools-LSFG is a Samsung Xclipse Vulkan compatibility layer based on
`WearyConcern1165/ExynosTools`, with additional hardening for coexistence with
GameNative's `lsfg-vk-android` runtime.

The repository intentionally produces **two different Android Vulkan products**.
They solve different integration problems and must not be installed
interchangeably.

## 1. General emulator / Vortek product

This is the upstream-style ExynosTools path for Winlator-style launchers and
other emulators that understand the Vortek `layerLibrary` + `layerName` package
model.

The executable built from this repository is:

```text
libVkLayer_VortekXclipse.so
```

with Vulkan layer:

```text
VK_LAYER_VORTEK_XCLIPSE
```

A complete importable driver bundle has this layout:

```text
meta.json
VkLayer_vortek_xclipse.json
vulkan.samsung.so
libVkLayer_VortekXclipse.so
INSTALL.txt
```

`vulkan.samsung.so` is the matching Samsung backend for the target device or
emulator. It is not generated by this repository and is intentionally not
invented or substituted in CI.

The workflow `.github/workflows/build-general-emulator-layer.yml` compiles the
actual `VkLayer_VortekXclipse` CMake target, validates the ARM64 ELF and Vulkan
loader exports, rejects RPATH/RUNPATH leakage, and publishes a **layer-only CI
artifact**. That CI artifact is for validation and integration; it is not a
standalone Samsung custom-driver bundle until paired with a matching backend.

To create a complete package after building the layer:

```bash
python scripts/package_emulator_driver.py \
  --build-dir build-android \
  --backend /path/to/vulkan.samsung.so \
  --output dist/ExynosTools-LSFG-General-Emulator.zip
```

For CI or launchers that already provide the Samsung backend:

```bash
python scripts/package_emulator_driver.py \
  --build-dir build-android \
  --layer-only \
  --output dist/ExynosTools-LSFG-General-Emulator-Layer.zip
```

## 2. GameNative LSFG Wrapper product

GameNative's LSFG path uses a different Vulkan integration boundary. The
workflow `.github/workflows/build-gamenative-wrapper.yml` builds a pinned Mesa
Wrapper ICD and packages:

```text
ExynosTools-LSFG-GameNative-1.2.0.wcp
```

That WCP contains `libvulkan_wrapper.so`, its ICD manifest, and
`libadrenotools.so`. It is a **GameNative Wrapper content package**, not the
Vortek/general-emulator driver above.

The GameNative patch preserves LSFG's shared-device feature chain, prevents the
wrapper from retrying device creation with `pNext = NULL` while LSFG is active,
and disables optional wrapper work that can interfere with frame generation.
See `docs/LSFG_GAMENATIVE_INTEGRATION.md`.

## LSFG compatibility boundary in the Vulkan layer

The general ExynosTools layer remains usable without GameNative. LSFG-specific
behavior activates only when both of GameNative's process markers are present:

```text
LSFG_PROCESS
LSFG_CONFIG
```

Without that pair, the layer follows its normal ExynosTools/Vortek behavior.
The LSFG path does not fabricate Vulkan capabilities and does not take ownership
of swapchain, presentation, or frame-generation objects.

## Core compatibility behavior

The layer retains the upstream ExynosTools functionality used on Xclipse GPUs,
including BC4/BC5/BC6H/BC7 virtualization, image-format compatibility,
AHardwareBuffer/external-memory safety, depth/stencil compatibility, pipeline
sanitization, VMA-backed staging, descriptor reuse, pipeline caching, and
DXVK/vkd3d-proton-related driver quirks.

The Samsung Vulkan driver remains the backend. ExynosTools is a Vulkan layer,
not a replacement kernel or userspace GPU driver.

## Android ARM64 build

The CI build uses Android NDK ARM64, Vulkan-Headers and
Vulkan-Utility-Libraries `v1.4.341`, the bundled VulkanMemoryAllocator headers,
and `glslc`.

A matching local build is:

```bash
cmake -S . -B build-android -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE="$ANDROID_NDK_HOME/build/cmake/android.toolchain.cmake" \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-29 \
  -DCMAKE_BUILD_TYPE=Release \
  -DEXYNOS_LAYER_USE_SUBMODULE_DEPS=ON \
  -DEXYNOS_LAYER_USE_LOCAL_VULKAN_REPOS=OFF \
  -DEXYNOS_LAYER_BUILD_SHADERS=ON \
  -DEXYNOS_LAYER_EMBED_SHADERS=ON

cmake --build build-android --target VkLayer_VortekXclipse -j2
```

Expected output:

```text
build-android/libVkLayer_VortekXclipse.so
```

Validate it with:

```bash
readelf -h build-android/libVkLayer_VortekXclipse.so | grep -E 'Class:|Type:|Machine:'
readelf -Ws build-android/libVkLayer_VortekXclipse.so | \
  grep -E 'vkGetInstanceProcAddr|vkGetDeviceProcAddr|vkNegotiateLoaderLayerInterfaceVersion'
readelf -d build-android/libVkLayer_VortekXclipse.so | grep -E 'RPATH|RUNPATH' && exit 1 || true
```

## Repository rules

- `src/**` belongs to the general Vulkan layer and must be validated by the
  general-emulator workflow.
- `ci/patch_gamenative_wrapper_lsfg.py` belongs to the GameNative Wrapper path.
- A GameNative Wrapper build must never be presented as proof that the general
  ExynosTools layer compiled or works.
- Stale V3.0 packagers and obsolete `libVkLayer_ExynosTools.so` /
  `VK_LAYER_EXYNOSTOOLS_bcn` naming are intentionally removed.
- Generated `.so`, `.zip`, `.wcp`, build directories, logs, probe captures, and
  local dependency checkouts must not be committed.

`tests/test_repository_product_boundaries.py` enforces the most important of
these separation rules.

## Target hardware

The primary target is Samsung Xclipse/RDNA-derived GPUs, including Xclipse 920,
940, 950, 960 and related generations where the same Vulkan behavior applies.
Compatibility still depends on the Vulkan capabilities and Samsung driver
revision exposed by the device.
